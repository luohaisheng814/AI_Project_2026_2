## 1. 这份文稿要回答什么

现场导游式的问答，难点不在「知道多少景点」，而在**在什么位置、什么条件下，只给一两个能立刻行动的选择**。这份文稿记录三件事：

1. 把「现场情境」翻译成「出行条件」的方法，以及条件缺失时怎么追问；
2. 实际怎么实现的（页面、接口、安装包三层）；
3. 实测结果与差距，包括哪些地方我们没做到、不装成做到了。

---

## 2. 方法：把现场情境转成出行条件

### 2.1 场景枚举

现场问句先被判成四类，不同类的第一步完全不同：

| 场景 | 典型问法 | 第一步 | 不该做的事 |
|---|---|---|---|
| A 已有目的地 | 「甘川文化村怎么去」「没云台交通」 | 直接给交通/路线 | 不要再问「你想去哪」 |
| B 请推荐 | 「附近有什么」「推荐一个地方」 | 先确认位置，再补 1–2 个条件 | 不要一次列 8 个景点 |
| C 条件不完整 | 「时间不够」「少走路」 | 沿用前文重排 | 不要从头再问一遍 |
| D 纯名词 | 「甘川文化村」 | 精简介绍 + 一句「要不要交通/门票」 | 不要输出完整攻略长文 |

### 2.2 条件优先级

条件不是越多越好，按「会不会改变结论」排序，只补会改变结论的那一项：

| 优先级 | 条件 | 为什么排这里 | 缺失时的处理 |
|---|---|---|---|
| P0 | 当前位置或出发点 | 没有起点，任何「附近」都不成立 | 申请定位；失败给手选起点 |
| P1 | 时间预算 | 30 分钟和半天，候选完全不同 | 默认「半天」并明说假设 |
| P2 | 交通方式 / 步行承受度 | 决定「海边线性景点」还是「山坡村落」 | 默认公共交通 + 可走 15 分钟 |
| P3 | 兴趣（拍照 / 日落 / 候鸟 / 渔港） | 同类景点里挑哪个 | 按所选玩法默认 |
| P4 | 同行人 / 人数 | 影响节奏与是否爬坡，不影响地点 | 不追问性别、不按性别推喜好 |

### 2.3 回答粒度

| 用户输入 | 回答结构 | 实测字数 |
|---|---|---|
| 只给景点名 | 一句话定位 + 2–3 条要点 + 一句追问 | 479 字（未登录） |
| 景点名 + 交通 | 换乘段 + 下车后步行 + 打车备选 | 1437 字（没云台交通） |
| 条件变更 | 新候选 1–2 个 + 变更理由 + 新路线 | 1012 字（时间不够→多大浦海水浴场） |
| 登录后同问 | 本地库 + 官网正文 + 来源列表 | 640 字（含 5 条来源） |

## 3. 分工边界：AI、定位、地图、资料各管一段

这一段是刻意的自我约束，避免把通用能力包装成「独创」：

- **AI 只做理解与表达**：判断场景、生成追问、组织理由与措辞；不编造距离、时间、营业状态。
- **定位只做筛选起点**：GPS 只回答「我大概在哪」，用来算直线距离、排出周边候选；**定位不等于实时营业，也不等于拥挤程度**。这是手机系统都有的能力，不是本项目的创新点。
- **地图只做路线确认**：页面给 `nmap://` 深链（导航 / 地点 / 检索三种），实际换乘、步行分钟数交给 NAVER 地图 App；没装 App 时退回网页地图与 Google。
- **资料只做来源与核对**：登录后并发抓沙下区官网（`contents.do?mId=…`）与本地分类库；抓不到就写「在线查询未获取到内容」，不拿旧印象补空。

同样地，**三语按钮不是新功能**：语言只决定表达，检索与生成始终先用中文完成，再整体翻译；翻译不增删条目、不改推荐顺序、专名用惯用译。这一点在上一轮已写进锁定规则，本轮没有改动。

「移动定位」在原始规范里仍标注为**待开发功能**。本版把它落在手机浏览器 / WebView 内的系统定位上，属实现层补齐，不是规范里承诺的独立模块。

## 4. 实现

### 4.1 手机页面（`mobile/index.html`）

- 顶部：中文 / 한국어 / EN 三语按钮；「本地模式 / 已联网」状态点；**登录 / 退出**按钮；服务端地址齿轮（从 APK 设置页进入时可改）。
- 流程条：`1 位置 › 2 条件 › 3 候选 › 4 路线`，随问答推进点亮，用户随时知道走到哪一步。
- 玩法 / 出行人数两栏：问答里说过的选项自动同步到下拉，也允许手动改。
- 8 条场景 chip：附近推荐、已有目的地、交通、开放时间、门票、拍照、换点等，覆盖 2.1 的四类场景。
- 候选卡：前 2 条带「推荐」徽章 + 当前条件下的理由 + 直线距离；其余折叠成「其余 N 个（点开看）」。
- 定位失败卡：橙色，给「重试定位」和「选择出发点」（下拉直接取 `/api/meta.spots`）。
- 回答尾部：`stripTail` 清掉模型自带的重复小标题，只保留结构化「资料来源 / 其它玩法补充推荐 / 你可能还想问」。

### 4.2 服务端（`mobile_app.py`）

| 接口 | 作用 | 关键返回 |
|---|---|---|
| `GET /api/meta` | 页面初始化 | 4 类玩法、6 组、8 个景点（含坐标） |
| `POST /api/nearby` | 周边候选 | 距离、`reason_key`、前 2 条 `recommended`、`origin_name` |
| `POST /api/chat` | 问答 | 回答正文、`online`、`concise`、`sources`、`trace` |
| `POST /api/login` `/register` `/logout` | 账号 | 与桌面 / 网页共用 `busan_travel.db` |
| `GET /api/me` | 登录态 | 用户名、是否联网 |

距离用 Haversine 算直线；通勤时间不写进答案，留给地图 App。

### 4.3 安装包（`android/`）

- 启动先落在 `setup.html`：填电脑地址（联网）或「离线使用」（跑包内 `data.js`）。
- `MainActivity` 把地址存进 SharedPreferences；`requestLocation()` 走 Android 运行时授权后回调网页；`nmap://` 等 scheme 交系统 App；主框架加载失败自动回设置页。
- 清单：`INTERNET` + `ACCESS_NETWORK_STATE` + 两个定位权限 + `usesCleartextTraffic="true"`（局域网 http 需要）。

### 5.3 两次失败与解释

1. **模拟器第一次点「附近景点」**：弹出系统定位授权，自动化环境无法代点「允许」，只能改由 `pm grant` + 模拟坐标验证链路；真实用户手动授权这一步未在自动化里点过。
2. **登录后那次问答的官网抓取失败**：手机端显示「官网 / 百科在线查询 在线查询未获取到内容」，而接口自测同一问句 `web=2`、含 saha 链接。判断为**单次抓取超时/被站点拦截**，不是登录态失效；页面对这种情况的处理是如实说明，没有编内容。这一点保留在「已知限制」里，不做粉饰。

## 7. 已知限制（如实记录）

1. **「请 2 名用户在手机完成相同任务」本轮未做**。当前环境无法组织真人，只有模拟器端到端 + 接口自测；下轮若要做，需要真人各跑一遍 A/B/C/D 四类场景并记录耗时与追问次数。
2. **系统定位授权弹窗未真点**：自动化环境点不了「允许」，改用 `pm grant` + 模拟坐标验证；「点按钮 → 授权 → 出卡片」这条真实手势链路未在自动化里走完。
3. **距离是直线**：页面写 0 km / 1.31 km 都是直线距离，不等于步行或公交距离；实际时间以 NAVER 地图为准。
4. **定位 ≠ 营业 / 拥挤**：没有接入实时营业状态与人流数据，页面不声称「现在人少」。
5. **官网抓取不稳定**：站点对 `zh-CN` 头返回 403，已固定韩文头，但仍有偶发超时；失败时如实标注。
6. **登录后用户名显示异常**：模拟器上登录 `admin` 后，状态行出现 `1234` 而不是 `admin`，尚未定位是显示名还是渲染取错字段，待核。
7. **联网模式依赖电脑**：手机与电脑需在同一 Wi-Fi，且电脑上服务在跑；模拟器场景额外需要 `adb reverse`。
8. **没云台坐标仍是入库值**：未用 NAVER 精校，0 km 会出现，属坐标精度问题，不是定位错误。
9. **桌面 tkinter 版**：只改了 `online=True` 一行，未启动窗口实跑。
